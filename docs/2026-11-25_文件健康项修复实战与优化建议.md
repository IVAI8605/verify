# 文件健康项修复实战记录与工具优化建议（2026-11-25）

> 场景：用查重助手 v4.1.2 对三个视频根（约 16.8 万文件）做「文件健康」检测后，批量修正后缀名与文件名。
> 本文记录实际做法、踩的坑，以及给 Verify 项目的改进建议。所有操作清单与回退账本在
> `_外置/备份/Verify健康修复_20261125-092956/`（工作区内，325M）。

## 二、有效性核实：不要盲信 Verify 的 suggest

这是本次最重要的经验。用 ffprobe 对全量做交叉验证，发现 **Verify 的建议有明显误判**：

| Verify reason / suggest | 数量 | ffprobe 实测 | 结论 |
|---|---|---|---|
| `mismatch` → `ts` | 419 | 全是 mpegts | ✅ 准确，照改无误 |
| `mismatch` → `mp3` | 86 | 全是 **aac** | ❌ 错！`.aac` 改 `.mp3` 反而制造错误 |
| `mismatch` → `3gp` | 83 | 标准 mp4 容器 | ❌ 无意义，`.mp4` 本来正确 |
| `unknown` → 无建议 | 86 | 68 条 mpegts、5 条 rm、5 条 mpeg、6 条打不开等 | ⚠️ 混合，需逐条实测 |

**教训**：批量执行前必须抽样 ffprobe 核对 suggest。Verify 的头部探测只认有限的容器特征，`data` 开头但实际是 mpegts 的、aac 误判成 mp3 的，都会误导批量操作。

## 三、踩过的坑（按发生顺序）

1. **认证 token 文件不是纯令牌**：`access-token.txt` 第一行是中文说明，令牌在第二行。用整个文件当 Bearer 会 401。应只读第二行。
2. **API 有并发闸门**：改名/撤销与自动巡检（scan）互斥，扫描进行中改名返回 409。需先查 `/api/tasks` 确认无 running 任务。这是保护机制，不是故障。
3. **撤销要先想清楚再点**：我曾对第一批 500 条做撤销验证，想改回去时撞上自动扫描（409），导致中间状态；后来等扫描结束补改成功。以后验证撤销要预留"改回去"的窗口。
4. **文件名批处理撞坏字符**：某批返回 400「路径包含无法识别的文件名字符」——非 UTF-8 文件名经 JSON 编码变成 U+FFFD，传回 API 对不上磁盘名。Verify 有保护但批量脚本没预筛。解决办法：拉结果后先过滤含 `\ufffd` 或控制字符的路径，单独走 fix-encoding 或保留。
5. **文件名批出现"失败"条目**：前批改了父目录名，后批用旧路径就找不到（原快照路径已失效）。health 计数降到 1 说明实际都处理了，但账本里的 failed 数不可直接当"没改成"。
6. **API 硬拒 unknown 类**：`planRename` 对 `ReasonUnknown` 直接拒绝（设计如此，防止瞎猜）。68 条 ffprobe 实锤是 mpegts 的也因此改不了。
7. **会话用户无媒体目录写权限**：attempt 直接 `os.rename` 报 Permission denied（[Errno 13]）。媒体卷属 verify 应用用户，只有走 Verify API 才能改。这是权限边界，不应绕过。

## 四、给 Verify 项目的优化建议（按优先级）

### P0 — 修正误判，避免"好心办坏事"

1. **aac 被建议成 mp3**：`CheckExt` 的音频识别逻辑应先用 ffprobe/文件头魔数区分 aac（ADTS `0xFF 0xF1` / ID3）与 mp3（`ID3` / `0xFF 0xFB`）。当前 86 条误判全部来自 `.aac` 文件。修前先跑 `_外置/备份/.../aac_misjudged.txt` 里的样本回归。
2. **mov/mp4 容器被建议成 3gp**：ffprobe 的 `mov,mp4,m4a,3gp,3g2` 是通用族名，`CheckExt` 不应据此建议 3gp。建议：只有文件头明确是 `ftyp3gp` 才建议 3gp，否则保持 `.mp4`。

### P1 — 增强容器识别，减少 unknown

3. **mpegts 识别加强**：68 条 `data` 开头的 mpegts 被判 unknown。mpegts 的同步字节 `0x47` 每 188 字节出现一次，检查头部若干偏移（0/188/376）即可确认，不必依赖首字节魔数。这能把大部分 unknown 转成 mismatch→ts。
4. **给 unknown 类"建议但不自动"的通道**：当前 unknown 完全拒绝改名，连 API 入参都不接受。建议加一个 `force` 显式标志 + 调用方确认，让"调用方已用外部工具（ffprobe）验证过真实类型"的场景能执行，同时保留审计与撤销。
5. **改名前用 ffprobe 二次确认（可选开关）**：对 mismatch/unknown 类，改名服务端先跑一次 ffprobe（配超时），拿 `format_name` 与 suggest 比对，一致才改。可配置 `verify_ext_probe=true`，默认关（避免依赖 ffprobe 的机器受影响）。

### P2 — 批量脚本友好性

6. **批量改名接口预筛坏字符路径**：与其在写到一半时 400 中断整批，不如入口处先把含 U+FFFD/控制字符的路径挑出，返回 `skipped` 列表让调用方继续其余。避免"一批 200 条因 1 条坏字符全失败"。
7. **改名结果里区分"失败"与"路径已失效"**：`syncRenamedIndex` 改父目录名后，同一快照里子文件的旧路径会失效。当前都算 failed，建议单列 `stale_path` 类别，避免误读。
8. **批量操作提供 dry-run 端点**：`/api/health/rename` 加 `dry_run: true`，返回每条的计划目标名与风险判断，脚本可先全量预演再执行。
9. **undo 的幂等提示**：重复撤销同一 task_id 时应返回"已撤销"而非错误，方便脚本重试。

### P3 — 权限与文档

10. **明确记录媒体卷需应用自身权限**：文档写明「媒体根目录由 verify 应用用户持有，外部脚本直接改名会被拒；一切写入必须走 Verify API」。避免后续再踩 [Errno 13]。
11. **健康结果导出加 `detected_format` 字段**：结果里带上实际探测到的格式（如 ffprobe 的 format_name），调用方不必再对每个文件跑一遍 ffprobe。

## 五、可复用的操作 SOP（下次照做）

1. **只读探测**：`/api/status` 看 auth；`/api/health/status` 看 counts；确认 `/api/tasks` 无 running。
2. **备份**：数据库 `verify.db` + WAL/shm + `config.json` + 全量健康结果快照，存工作区 `_外置/备份/`。
3. **交叉验证**：对每类 suggest 抽样（或全量）跑 ffprobe，确认建议正确。**aac/3gp 类必须验**。
4. **分类分批**：只把"实测与 suggest 一致"的类别交给 API；每批 200，记 task_id。
5. **预筛坏字符**：路径含 U+FFFD/控制字符的挑出，不进批量。
6. **执行 + 对账**：每批记 done/failed/task_id；完成后用 ffprobe/文件存在性核对。
7. **回退预案**：三个 `fix_*_state.json` 是撤销账本；`fix_health.py undo <task_id>` 可整批还原；数据库备份是最后兜底。
8. **验证撤销链**：先在少量条目上试一次撤销 + 改回，确认 inode 不变、内容无改动，再放量。

## 六、本次未能处理及原因

- **68 条 mpegts（unknown 类）**：ffprobe 实锤是 ts，但 Verify 的 API 硬拒 unknown、会话用户又无媒体目录写权限，两条路都堵。需 Verify 加 force 通道（建议 4）或由应用侧执行。
- **6 条打不开的 data 文件**：可能是下载不完整/加密封装，无法确认目标格式，保留原样。
- **1 条坏字符文件名**：API 传参会被替换字符破坏，保留原样（清单 `name_badchars.txt`）。

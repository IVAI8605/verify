# verify × DC5 实际效率对比测试方案（真实场景版）

> 起草时间：2026-11-11 03:05（v2，覆盖 02:40 的镜像数据集版本）
> 原则变更：**不追求公平对比，只测实际使用效率**。真实场景是：verify 在 NAS 本地处理海量媒体文件；DC5 在 Windows 上通过 SMB 共享处理同一批文件。两者各自的"实际用法"就是被测对象。
> 依据：DC5 产品文档、内部 Trae 操控能力评估、2026-11-11 03:00 只读探测

## 1. 已核实的环境事实（2026-11-11 只读探测）

| 项 | 值 | 来源 |
|---|---|---|
| 生产库规模 | **约 17 万文件 / 数十 TB** | 生产实例 `/api/status` |
| 扫描根 | 三个数据卷上的共享目录（下文记作「数据卷 A/B/C」） | 同上 |
| 同名重复 | 万余组 / 浪费数 TB | 同上 |
| 精确重复 | 16 组 / 36 文件 / 浪费 1.5 GB（min_size=1024 下的现有结果） | 同上 |
| 视频分析 | `video_enabled=false`（未做过视频 pass） | 同上 |
| SMB 映射 | `U:`、`V:`、`W:` 三个盘符分别映射到上述三个共享（`\\<NAS主机>\<共享名>`，本机已连通） | `Get-SmbMapping` |
| 卷容量 | 三个数据卷均在十 TB 量级，测试时各卷余量充足 | `/api/status` volumes |

**规模裁决**：数十 TB 全量读对两边都不现实（verify 本地聚合读 ~17h，DC5 走千兆 SMB ~79h，均为推断）。因此档位设计为：**全库只做不读内容的比对（档 A），读内容的比对在子集上做（档 B/C）**。

## 2. 任务档位

| 档位 | 任务 | DC5 侧 | verify 侧 | 范围 | 读内容? |
|---|---|---|---|---|---|
| **A（主对比）** | 同名文件查重（实际场景第一步：枚举 16.8 万文件 + 按名分组） | Search Criteria 勾「Same file name」，存状态 `/load` | `min_size=1024` 全库 quick 扫描 → `mode=name` 分组 + 导出 | **全库数十 TB** | 否（纯元数据） |
| **B** | 子集内容查重（全文哈希） | `/m` 常规模式，`/i` 指子集 | `mode=exact`，volumes 指子集 | 选定子目录（300GB–1TB） | 是 |
| **C（可选）** | 子集视频相似 | `/mv` 视频模式 | `video_enabled=true` + video pass + `mode=video` | 同档 B 子集 | 是（解码抽样） |

- **档 A 是核心**：它就是用户的真实工作负载（同名组万余个），且两边都不读文件内容，规模可全量；耗时差异主要反映**枚举通道差异**（SMB 元数据 vs 本地文件系统）。
- **档 B 反映读吞吐差异**：SMB 网络读 vs 本地盘读 + BLAKE3。
- **档 C 算法不同**（DC5 视频模式 vs verify 音频指纹+dHash），只比耗时与检出量级，结果不预期一致。

### 档 B/C 子集选定规则（跑前执行）

用档 A 跑完的 verify 临时实例调 `GET /api/folder/stats`（只读），从三个扫描根的顶层子目录中挑**总字节 300GB–1TB、以视频为主**的一个子目录；DC5 与 verify 都只指向它。选定后把路径与实测字节数记入报告。

## 3. 两侧执行方式

### 3.1 verify 侧（NAS 本地，临时实例）

- **不碰生产实例（8898）**。起临时实例：HEAD 重新交叉编译，`-data` 指向**测试目录下的数据目录**（不是 /tmp——临时 db 会到 300MB 量级，与生产同量级）：
  - 数据目录：SSD 卷测试目录下的 `dc5-bench-verify-data/`（`verify.db` 预计 300–400MB）
  - 端口 18899，随机 32 位令牌
- `config.json`：`volumes` = 三个真实扫描根（档 A）或子集（档 B/C），`min_size=1024`，`watch=false`，`sleep_friendly=true`（禁自动扫描），视频开关按档位
- 扫真实库只读磁盘文件，写自己的临时 db——生产库零接触
- 每轮冷态：停实例 → 删临时 `verify.db*` → 重启（测试数据目录，可重建）
- 档 A 流程：`POST /api/scan {"mode":"quick"}`（枚举+头尾 4KB 预哈希，读量 ≈ 16.8万×8KB ≈ 1.3GB）→ 轮询至完成 → `GET /api/groups?mode=name` 分页拉取 → `POST /api/export {"mode":"name","format":"dc5"}`
- 档 B 流程：`POST /api/scan {"mode":"full"}`（子集全文 BLAKE3）→ `mode=exact` 导出
- 档 C 流程：开视频后 full 扫描含 video pass（ffmpeg 本地解码）→ `mode=video` 导出

### 3.2 DC5 侧（Windows，SMB，命令行全自动）

依据 DC5-MCP操作备忘.md 第三节（官方参数，2026-11-02 已实测）：

```powershell
# 档 A（同名，全库三个根）
& "<DC5 程序目录>\Duplicate Cleaner 5.exe" `
  /data "<本机工作目录>\dc5data" `
  /i "U:\" /i "W:\" /i "V:\<子目录>" `
  /load "同名查重状态" /csv "<输出目录>\dc5-A-r<N>.csv" /scan /close
```

- 盘符路径用现有映射（U:/V:/W:）；若 DC5 对盘符根 `/i "U:\"` 处理异常，改用 UNC `\\<NAS主机>\<共享名>`（跑前实测确认）
- **同名模式**：GUI 里 Search Criteria → File name → "Same file name"，关闭内容哈希类条件，**最小文件大小过滤设为 1KB**（与 verify `min_size=1024` 对齐），存成扫描状态供 `/load` 复用
- 档 B：`/m` 常规模式 + 子集目录；档 C：`/mv` 视频模式 + 子集目录
- 每轮前置检查：无 DC5 残留进程（单实例限制）；首次用 `/data` 指定目录会弹免责声明，Windows-MCP 点掉一次即可

## 4. 计时口径

按"不考虑公平、只测实际"的原则，**主指标就是端到端实际耗时**：

| 档位 | DC5 | verify |
|---|---|---|
| A | 进程启动→进程退出（含 SMB 枚举全程） | quick 扫描墙钟（触发→running=false）+ 分组导出耗时，两者相加为端到端 |
| B | 同上 | full 扫描墙钟 + 导出 |
| C | 同上 | full 扫描（含 video pass）墙钟 + 导出 |

- verify 另记服务端日志三段耗时（枚举/预哈希/全量校验）作辅助列，不参与主对比
- DC5 日志不记扫描耗时（2026-11-11 只读核实），无法拆阶段，如实标注
- 每档 3 轮取中位数；轮间 verify 冷态重建，DC5 每轮新 CSV 文件名
- **不对等即结论**：SMB 与本地盘的差距本身就是测试目的，不做任何"扣除启动开销"类修正

## 5. 资源采样

| 侧 | 方法 | 指标 |
|---|---|---|
| DC5 | PowerShell 后台作业每 1s `Get-Process`；另记 SMB 网络计数器（`Get-Counter '\Network Interface(*)\Bytes Received/sec'` 或按网卡） | 峰值 RSS、累计 CPU 秒、墙钟、期间下行流量估算 |
| verify | NAS 后台循环每 1s 读 `/proc/<pid>/stat` 与 `/proc/<pid>/io`（普通用户可读，无需 sudo） | 峰值 RSS、累计 CPU 秒、读 IO 字节 |

跑前实测一次**链路速率**：从 `U:` 读一个 ≥1GB 文件计时（`Measure-Command { Get-Content ... -Raw }` 或 robocopy 单文件），把实测 MB/s 记入报告——它是档 B DC5 耗时的解释变量。

## 6. 结果比对

两边都产出 DC5 格式 CSV（verify 的 `format:"dc5"` 导出与 DC5 必需列契约一致，`internal/export/export.go:24` 已核实）：

- **档 A（同名）**：预期两边高度一致（同名是确定性规则）。比对：文件集合差（路径归一：`W:\` ↔ `/vol6/<共享目录>` 等三个前缀映射，分隔符统一）、组数、每组副本数分布、浪费字节数。差异抽 20 条人工仲裁。
- **档 B（内容哈希）**：同组判定两边都基于文件内容，预期组结构一致；hash 列**不跨工具比值**（算法不同），只做组内一致性校验。
- **档 C（视频相似）**：算法不同，**只比量级**（组数、检出文件数、各自标出的重复对抽样 10 组人工看是否合理），不做组级等价断言。

## 8. 安全红线

1. **不删除任何文件**：DC5 只扫描导出，绝不进入 File Removal；verify 临时实例不调用任何写接口
2. verify 临时实例扫真实目录 = 只读磁盘；生产实例与其 `verify.db` 零接触
3. DC5 的 `/data` 用专用目录，不指向用户日常的 `%APPDATA%` 或便携版默认数据，避免污染既有扫描状态
4. 临时实例令牌不写进报告；跑完后清理清单（临时 db、测试目录内产物）列给用户决定

## 9. 预期（推断，跑前立此存照）

- 档 A：verify 本地枚举 16.8 万文件推断 1–10 分钟（3000 文件实测 107ms 线性外推偏乐观，冷元数据会慢）；DC5 走 SMB 枚举同量文件推断 10–60 分钟（受目录结构与 SMB 往返影响大）。**若差距 <2 倍属意外**，先核对 DC5 是否意外开启了内容哈希。
- 档 B：耗时比 ≈ (链路速率⁻¹ + DC5 哈希) vs (本地读 + BLAKE3 @ 878 MiB/s 实测)；千兆链路下 DC5 受网络支配。
- 档 C：两边耗时都会被解码支配，量级可能接近；检出组数不预期一致。
